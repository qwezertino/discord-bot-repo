## Что это за проект

Мы выделили существующую Python-панель из соседнего репозитория
`../perimeter_fivem/tools/discord_bot` в самостоятельный проект.
Исходный Perimeter не меняли. Здесь сохранены исходники и тесты, сделан нейтральный
брендинг. Сейчас приложение по-прежнему обслуживает **одного бота**: несколько
ботов, профили проектов и интеграция с KCD:MP пока не реализованы.

Стек: Python 3.12+, FastAPI, discord.py, SQLite, Jinja2, обычные HTML/CSS/JS.
Оставляем Python: переписывать рабочую панель на Go или менять frontend-стек
без необходимости не нужно. Предпочтение — понятная архитектура и рабочий продукт.

Уже есть:

- создание, изменение и удаление собственных сообщений бота;
- редактор embed, Markdown, вложения, предпросмотр, упоминания;
- выбор Discord-сервера, канала и ролей;
- импорт собственных сообщений из истории каналов;
- роли за реакции, включая снятие роли при удалении реакции;
- каталог emoji и журнал действий;
- SQLite для публикаций, вложений и правил;
- локальная веб-панель с проверками origin и опциональным HTTP Basic Auth;
- запуск на Linux/Windows и пример systemd-сервиса.

Основные файлы:

- `app/web.py` — FastAPI, lifecycle, middleware, маршруты;
- `app/discord_service.py` — Discord-клиент и все операции;
- `app/database.py` — SQLite и сохранённые сущности;
- `app/config.py` — настройки, сейчас один `DISCORD_BOT_TOKEN`;
- `app/models.py` — входные модели;
- `app/templates/index.html`, `app/static/app.js`, `app/static/style.css` — интерфейс;
- `tests/` — существующие тесты;
- `run.py`, `run.sh`, `run.bat`, `pyproject.toml` — запуск и зависимости.

Реальные токены, `.env`, старая SQLite и вложения намеренно не скопированы.
Приложение ещё не подключено к реальному боту в этом новом проекте.

## Что нужно сделать

Доработай существующую панель в общую панель управления несколькими нашими
Discord-ботами. Например, отдельные боты Iron Crown и Perimeter, с возможностью
добавить следующие. Это личная/командная панель владельца, не публичный SaaS.

Сначала исследуй код и коротко опиши выбранную архитектуру. Затем реализуй
первый законченный этап — поддержку нескольких ботов с сохранением текущих
инструментов. Не останавливайся на плане: подготовь рабочий код, миграции,
тесты и документацию. Начинай без реальных токенов, с изолированных тестов.
Недостающие параметры спрашивай по ходу, продолжая независимую работу.

### Профили и жизненный цикл ботов

1. Добавление/редактирование профиля бота: внутренний ID, отображаемое имя,
   Discord Application ID, ссылка на секрет, включённость и настройки.
2. Переключатель активного бота в панели. Дальше пользователь выбирает
   Discord-сервер, канал и инструмент. Показывай, от чьего имени выполняется действие.
3. Один управляемый Discord-клиент на каждого включённого бота в одном приложении.
   Подключение, отключение, переподключение, состояние и понятные ошибки.
   Переключение интерфейса не должно запускать нового клиента.
4. Ошибка токена, intents или подключения одного бота не должна выключать остальных.
   Корректно закрывай задачи и соединения при остановке приложения.
5. Один бот может присутствовать на нескольких Discord-серверах. Выбор активного
   бота в браузере не является доказательством прав: backend проверяет принадлежность
   канала/сообщения/роли выбранным боту и серверу.

### Данные и миграция

- Все публикации, вложения, правила reaction roles, импорт и аудит должны иметь
  однозначного владельца-бота. Продумай нужные ключи и индексы.
- Операции над ID сущности другого бота должны отклоняться. Изоляция нужна на
  backend и в SQL, не только в фильтре интерфейса.
- История импорта одного бота не должна перезаписывать историю другого.
- Подготовь миграцию текущей одно-ботовой схемы на профиль первого бота без
  потери данных. Не сбрасывай базу. Новая пустая установка тоже должна работать.
- Сохрани возможность понятного перехода с текущего `DISCORD_BOT_TOKEN`.
- Токены не возвращать через API, не писать в логи/аудит, не хранить открытым
  текстом в общей SQLite. Для первого этапа допустимы ссылки на env-переменные
  вида `IRON_CROWN_BOT_TOKEN`, `PERIMETER_BOT_TOKEN`. Не создавай обязательную
  сложную инфраструктуру управления секретами ради двух личных ботов.
- Сохрани ID Discord строками, особенно при передаче в JavaScript.

### Интерфейс

- Сохрани существующие инструменты: сообщения, embed, вложения, импорт,
  упоминания, emoji, reaction roles и журнал.
- Дай понятный выбор бота, индикатор состояния и настройки его профиля.
- При переключении бота обновляй доступные серверы/каналы/роли, черновики и
  историю. Поздний ответ старого запроса не должен попасть в новый профиль.
- Исключи случайную отправку сохранённого черновика от другого бота.
- Пустая установка без токенов должна объяснять настройку, а не показывать
  бесконечное подключение или падать при старте.
- Проверки новых функций выполняй без настоящих публикаций и выдачи ролей.
  Не отправляй тестовые сообщения в живые Discord-серверы без моего задания.

### Игровые интеграции — отдельный последующий этап

Общая панель должна работать независимо от игровых проектов. Подготовь понятную
точку подключения интеграций, но не строй большой плагин-фреймворк заранее.

В соседнем `../kcd2server` уже реализована и проверена игроком привязка Discord:

- `docker/discord_auth.py` — OAuth callback и worker;
- `server/gamemodes/basicrp/modules/accounts/discord.lua` — игровой шлюз;
- `migrations/038_discord_auth.sql` — схема;
- PostgreSQL: `player_discord_links`, `discord_auth_requests`, `discord_auth_history`;
- настройки в `hosting.settings`, scope `basicrp`, раздел `auth.discord`;
- пароль игрового аккаунта сохранён;
- допуск по ролям «Тестер» или «Команда проєкту»;
- полная админка по «Тех. адмін» или «Адмністратор», дополнительно нужна роль допуска;
- при повторных входах и во время игры бот проверяет роли через REST;
- локально работает временный HTTPS-туннель. Его адрес не постоянный: получать
  текущий адрес из настроек, не зашивать значение из прошлой переписки.

Для этого будущий адаптер панели сможет показывать игровые привязки, состояние
OAuth, роли допуска/админки и историю проверок. Источником истины остаётся
PostgreSQL игры. Не переносить игроков в SQLite панели, не дублировать пароли,
не сбрасывать привязки и не заменять действующий OAuth-сервис при реализации
первого этапа. REST-проверки игры и Gateway-клиент панели могут использовать одного
бота, но нужно учитывать общие API rate limits. Админ-панель остаётся закрытой;
публичный callback не должен открывать её в интернет.

Второй игровой проект — `../perimeter_fivem`. Интеграцию с ним проектировать
отдельно: сейчас в общей панели нет готового адаптера к FiveM.

## Критерии готовности первого этапа

- Два тестовых профиля ботов работают независимо; одиночный профиль тоже.
- Существующие функции перенесены на выбранного бота без регрессий.
- Проверены изоляция данных и API, lifecycle клиентов, ошибка одного бота,
  поздние ответы при переключении, идемпотентный импорт и миграция старой базы.
- Пройдены существующие и новые осмысленные тесты; тестовые базы изолированы.
- Проверены JavaScript и запуск локального интерфейса без реального Discord.
- Документация содержит чистую установку, секреты, запуск двух ботов, настройки
  intents/прав и переход со старой панели.
- В конце сообщи, что реализовано и проверено, что требует реального бота,
  и какие данные нужны от меня. Реальные токены в чат не запрашивать.

Соседние игровые серверы и старую панель не изменять и не перезапускать.
